# 1. 배경

## 1.1 네이버 로컬검색의 변화

2026년 9월 17일 네이버는 네이버지도 앱에 **플레이스 에이전트**를 정식 출시했다.

공식 발표상 플레이스 에이전트는 자연어 문장에서 여러 조건을 동시에 해석하고, 이용자의 위치 및 대화 맥락을 바탕으로 적합한 장소를 추천하며, 네이버 예약 이용 업체는 대화 안에서 날짜·시간·인원까지 지정해 예약 신청으로 연결할 수 있다.

네이버가 공식적으로 설명한 장소 추천의 데이터 기반에는 다음이 포함된다.

- 주소
- 영업시간
- 메뉴
- 전화번호
- 플레이스 업체정보
- 방문자 리뷰
- 블로그 후기
- 예약 가능 여부
- 이용자 위치
- 대화 맥락

공식 자료:
- NAVER 보도자료, 2026-09-17  
  https://navercorp.com/media/pressReleasesDetail?seq=10034667

이 변화의 의미는 기존의 `지역명 + 업종` 중심 검색 외에 아래와 같은 **상황형·조건형 장소 탐색**이 독립적인 유입 경로로 생겼다는 것이다.

예:
- 주차 편한 한식당
- 아이와 가기 좋은 카페
- 반려동물 동반 가능한 카페
- 혼자 조용히 책 읽기 좋은 카페
- 예약 가능한 미용실
- 오늘 저녁 바로 예약 가능한 식당

단, 네이버는 **플레이스 에이전트의 추천 알고리즘, 가중치, 랭킹 공식**을 공개하지 않았다.

따라서 동네장사는 이를 `AI 추천 순위 예측`으로 표현해서는 안 된다.

## 1.2 AI 브리핑과 리뷰 구조화

네이버는 이미 이용자가 남긴 리뷰를 AI가 요약하는 **플레이스 AI 브리핑**을 운영하고 있다.

공식적으로 확인되는 사항:

- 최신 리뷰를 AI가 요약한다.
- AI 브리핑은 실험 단계이며 정보가 부정확할 수 있다.
- AI 브리핑 정보는 플레이스 검색, 업체 상세, 통합검색 등 다른 서비스에서 활용될 수 있다.
- AI 브리핑 노출을 허용한 업체는 관련 서비스에서 노출 기회가 넓어질 수 있다고 네이버가 안내했다.
- 2026년에는 프랜차이즈 식당 및 일부 숙박업종까지 적용 범위가 확대됐다.

공식 자료:
- https://new.smartplace.naver.com/notices/927
- https://new.smartplace.naver.com/notices/1059
- https://new.smartplace.naver.com/notices/967

네이버의 Place+ AI 리뷰 통계에서는 리뷰를 아래 9개 테마와 세부 속성으로 AI 분석한다.

- 음식
- 메뉴
- 가격
- 분위기
- 매장
- 시설
- 좌석
- 서비스
- 운영

그러나 네이버 스스로 AI 리뷰 분석 결과가 일부 부정확할 수 있음을 명시하고 있다.

공식 자료:
- https://new.smartplace.naver.com/notices/945

따라서 동네장사가 자체적으로 리뷰 문장을 단순 키워드 매칭해 `긍정/부정`, `뷰 좋음`, `조용함` 등으로 판정하는 기능은 이번 Phase에서 구현하지 않는다.

# 2. 이번 업데이트의 제품 원칙

## 2.1 기존 기능을 대체하지 않는다

기존 동네장사의 핵심은 다음이다.

> 특정 키워드에서 실제 상위 업체를 수집하고  
> 내 매장과 경쟁업체 사이의 정량적 Gap을 보여준다.

이 차별점은 유지한다.

신규 기능은 다음 질문에 답하는 보조 진단이다.

> **“네이버 AI가 장소를 이해하고 조건형 추천을 만들 때 활용할 수 있는 정보가 우리 매장에 얼마나 갖춰져 있는가?”**

---

## 2.2 “AI 추천 점수”를 만들지 않는다

금지:
- AI 추천 점수 82점
- AI 상위노출 확률 73%
- AI 추천 예상 순위 3위
- 이 항목을 채우면 AI 순위 상승
- AI 알고리즘 점수

이유:
네이버가 AI 추천 알고리즘의 평가 기준·가중치·순위 공식을 공개하지 않았다.

허용:
- 확인됨
- 보완 권장
- 확인 불가
- 해당 없음
- 경쟁업체 대비 등록률
- 공식적으로 AI 추천에 활용되는 정보인지 여부
- 데이터 수집 가능 여부

---

## 6.4 그룹 D — AI 브리핑

### R&D 우선 검증 항목

- AI 브리핑 존재 여부를 외부 공개 페이지에서 수집할 수 있는가
- AI 브리핑 텍스트를 안정적으로 추출할 수 있는가
- 업종별 DOM/API 필드가 동일한가
- 로그인/기기/AB 테스트에 따라 달라지는가
- 캐시 가능한가

수집이 검증되면 Phase 1 후속 패치로 다음을 표시할 수 있다.

예:

**AI 브리핑**
- 상태: 노출 중
- 네이버가 요약한 주요 특징: `...`
- 마지막 확인: YYYY-MM-DD

주의:
AI 브리핑 내용을 다시 긍정/부정 점수로 해석하지 않는다.

### 표시 고지

> AI 브리핑은 네이버 AI가 리뷰 등을 요약한 정보이며 실제 이용 경험과 다르거나 부정확할 수 있습니다.

---

## 6.5 그룹 E — 예약 및 행동 연결

후보:

- 네이버 예약
- 스마트오더
- 전화
- 톡톡

가장 중요한 것은 **예약 사용 여부가 추천 순위를 높인다고 표현하지 않는 것**이다.

허용 문구:

> 플레이스 에이전트는 네이버 예약 이용 업체의 경우 대화 중 예약 신청까지 연결할 수 있습니다.

금지:

> 네이버 예약을 사용하면 AI 추천 순위가 올라갑니다.

# 7. 요약 판정 방식

## 7.1 단일 종합점수 금지

`AI 추천 준비도 87점` 같은 점수는 만들지 않는다.

## 7.2 권장 UI

### 방식 A — 체크리스트

- 업체 기본정보: 5/6 확인
- 장소 속성: 3/5 확인
- 소비자 리뷰 신호: 확인
- AI 브리핑: 확인 가능 / 미확인
- 예약 연결: 사용 중 / 미사용

### 방식 B — 상태 배지

- 확인됨
- 보완 권장
- 확인 불가
- 해당 없음

권장: A + B 조합.

## 7.3 종합 문장

예:

> AI 장소 추천에 활용될 수 있는 기본 정보는 대부분 확인됩니다. 다만 상위 경쟁업체에서 흔히 등록된 주차·예약 정보 중 일부가 현재 확인되지 않습니다.

이 문장은 **경쟁사 실측 비교가 있을 때만** 사용한다.

1단계 단독 진단에서는:

> AI 장소 추천에 활용될 수 있는 기본 정보를 점검했습니다. 누락 항목은 실제 제공 여부를 확인한 뒤 스마트플레이스에서 보완할 수 있습니다.

# 9. 리뷰 원문 분석 — 이번 구현에서 제외

## 9.1 제외 이유

아래 문장은 단순 키워드 사전으로 정확하게 분석하기 어렵다.

- `뷰가 좋다길래 왔는데 그닥...`
- `여기 완전 뷰맛집`
- `조용해서 너무 무서워요`
- `주차 편하다고 누가 그랬냐`
- `뷰는 미쳤는데 커피 가격도 같이 미쳤다`

단어 존재 여부만으로 판단하면 다음 오류가 생긴다.

- 속성 존재와 감정을 혼동
- 부정문 처리 실패
- 반어 처리 실패
- 신조어 처리 실패
- 문장 내 여러 속성의 감정 혼합
- 문맥 의존 표현 오판

## 9.2 일반 코드 분석의 한계

형태소 분석 + 동의어 사전 + 부정어 사전 + 접속어 규칙으로 일부 구현은 가능하다.

그러나 운영 단계에서 규칙이 계속 증가하고, 한국어 구어체·반어·축약·신조어를 모두 안정적으로 처리하기 어렵다.

따라서 동네장사의 핵심 제품 기능으로 자체 규칙기반 감성분석기를 만드는 것은 범위 밖이다.

## 9.3 LLM 사용 가능성

향후 아래 형태로 실험은 가능하다.

입력:
리뷰 N개

출력:
```json
{
  "attribute": "view",
  "sentiment": "negative",
  "confidence": 0.91,
  "evidence": "뷰가 좋다길래 왔는데 그닥"
}
```

그러나 아래 문제를 검증해야 한다.

- 비용
- 응답시간
- 리뷰 원문 전송 정책
- 개인정보
- 재현성
- 모델 변경
- 오분류
- 대량처리 비용

## 9.4 R&D 통과 조건

리뷰 분석 제품화는 아래 순서를 반드시 따른다.

1. 리뷰 원문 수집 가능성 확인
2. 업종별 샘플 리뷰 확보
3. 사람이 직접 정답 라벨 작성
4. 최소 500~1,000건 수준 테스트셋 구성
5. 규칙기반 / 소형 분류모델 / LLM 비교
6. 속성 추출 정확도 측정
7. 감정분석 정확도 측정
8. 오분류 패턴 검토
9. 운영비 계산
10. 제품화 여부 별도 승인

**사용자 승인 없이 구현하지 않는다.**

# 12. 상담 전환 설계

이번 업데이트 목적은 A. 무료진단 강화 + B. 컨설팅 리드 확보다.

따라서 AI 진단 결과를 모두 무료로 보여주되, **원인→우선순위→실행계획 전체를 무료 공개하지 않는다.**

## 12.1 무료 공개

- 어떤 정보가 확인되는지
- 어떤 정보가 누락됐는지
- 네이버가 공식적으로 어떤 정보들을 활용한다고 밝히는지
- 경쟁사 대비 등록률(후속 구현 시)

## 12.2 리포트/상담 영역

예:

> 검색순위 Gap뿐 아니라 AI 추천에 활용될 수 있는 플레이스 정보 중 보완할 항목이 확인됐습니다.

CTA:

> **내 매장 맞춤 개선순서 무료 리포트 받기**

기존 이메일 리포트 퍼널을 재사용한다.

새로운 개인정보 입력이나 별도 상담폼을 만들 필요는 없다.

# 13. 데이터 모델 권장안

구현 전 실제 수집 필드를 먼저 확인한다.

권장 개념 구조:

```ts
type AiRecommendationAudit = {
  eligible: boolean;
  industryGroup: string | null;

  officialSignals: {
    businessHours: AuditField;
    phone: AuditField;
    address: AuditField;
    menuOrProducts: AuditField;
    description: AuditField;
    directions: AuditField;
    reservation: AuditField;
  };

  placeAttributes: {
    parking?: AuditField;
    petFriendly?: AuditField;
    noKids?: AuditField;
    privateRental?: AuditField;
    corkage?: AuditField;
    kidsMenu?: AuditField;
    anniversaryBenefit?: AuditField;
  };

  consumerSignals: {
    visitorReviewCount?: number | null;
    blogReviewCount?: number | null;
    keywordReviewTop?: Array<{
      label: string;
      count: number | null;
    }>;
    reviewMediaCount?: number | null;
    textReviewCount?: number | null;
  };

  aiBriefing: {
    collectible: boolean | null;
    visible: boolean | null;
    text: string | null;
    checkedAt: string | null;
  };

  notes: string[];
};

type AuditField = {
  status: "present" | "missing" | "unavailable" | "na";
  value?: unknown;
  source?: string;
};
```

실제 데이터 모델은 현재 scraper 반환 구조와 중복되지 않도록 최소 변경한다.

# 14. API 변경 원칙

## 14.1 `/api/place`

신규 AI 추천 진단은 1단계 내부이므로 원칙적으로 `/api/place` 응답 안에 포함한다.

별도 API를 만들지 않는 것을 우선 검토한다.

예:

```json
{
  "place": {},
  "aiRecommendationAudit": {}
}
```

## 14.2 수집비용이 큰 항목

AI 브리핑 등 별도 페이지 요청이 필요한 경우:

- 기본 `/api/place` 속도를 크게 악화시키면 안 된다.
- 우선 lazy-load 또는 후속 API 분리를 검토한다.
- 기존 24시간 KV 캐시 정책을 활용한다.
- 매 진단마다 동일 데이터를 반복 요청하지 않는다.

# 15. UX 원칙

1. 신규 섹션 때문에 1단계 로딩시간이 크게 늘어나면 안 된다.
2. “AI”를 과장된 마케팅 문구로 사용하지 않는다.
3. 네이버 공식 점수처럼 보이는 게이지 차트 금지.
4. 색상은 상태 표현용으로만 사용한다.
5. 누락된 정보는 곧바로 “문제”라고 하지 않는다.
6. 실제 서비스를 제공하지 않는 업체에 기능을 채우라고 유도하지 않는다.
7. `미등록`과 `수집 실패`를 반드시 구분한다.
8. 업종에 해당하지 않는 속성은 `해당 없음` 처리한다.
9. AI 브리핑의 부정확성 가능성을 고지한다.
10. 기존 2단계 Gap 분석 CTA가 신규 섹션 때문에 묻히지 않게 한다.

# 20. 성공 기준

이번 업데이트는 “AI 기능을 많이 만드는 것”이 목표가 아니다.

아래 조건을 만족하면 성공이다.

### 사용자 측

1. 사장님이 기존 진단에서 보지 못했던 `AI 추천 관련 정보 상태`를 이해한다.
2. 무엇이 실제로 등록되어 있고 무엇이 비어 있는지 알 수 있다.
3. 공식 확인 사실과 동네장사 해석을 구분할 수 있다.
4. AI 추천 순위 보장 서비스라고 오해하지 않는다.
5. 부족 항목이 있으면 맞춤 개선 리포트 또는 상담으로 자연스럽게 연결된다.

### 서비스 측

1. 기존 1단계 이탈률을 악화시키지 않는다.
2. `/api/place` 응답 시간이 과도하게 늘지 않는다.
3. 네이버 차단 위험을 증가시키지 않는다.
4. 수집 실패를 `미등록`으로 오판하지 않는다.
5. 기존 Gap 분석의 차별성을 유지한다.
